# FlowCheck security model

FlowCheck sends real requests to systems you configure. Running locally is **not** treated as safe by default.

## The FlowCheck server (implemented in phase 1)

| Threat | Defence |
|---|---|
| Other machines on the network | Listens on `127.0.0.1` only |
| DNS rebinding (a web page resolving its own hostname to 127.0.0.1) | `Host` header must be `127.0.0.1:<port>` or `localhost:<port>`, else `403 HOST_NOT_ALLOWED` |
| Cross-site requests from any open browser tab (CSRF) | POST/PUT/PATCH/DELETE require an `Origin` of the FlowCheck UI; missing or foreign Origin → `403 FORBIDDEN_ORIGIN`. GET never changes state |
| Cross-origin reads | No CORS headers are ever sent |
| Serving attacker-controlled content from our origin | Artifacts only via `/api/runs/:runId/artifacts/:artifactId`, path generated by the server and checked to stay inside the artifacts root, `X-Content-Type-Options: nosniff`, `Content-Security-Policy: sandbox`, non-images as attachments |
| Local processes calling the API | **Not yet defended.** Phase 5 adds a bootstrap token turned into an HttpOnly SameSite=Strict cookie |

## Test targets

- Only `http` and `https`.
- Every browser request (document, subresources, redirect hops) goes through a Playwright route: origins outside the environment's allowlist are aborted and recorded in the step evidence.
- The allowlist is the frontend and API base URL origins plus explicitly added origins (e.g. a CDN).
- API steps: the path is appended to the API base path (protocol-relative `//host`, backslashes and `..` are rejected); the final origin must be allowlisted; redirects are **not** followed (`maxRedirects: 0`), so a redirect cannot move credentials to another origin.
- Service workers are blocked (`serviceWorkers: 'block'`) because they could bypass request interception.

### SSRF protection

- The hostname is resolved and **every** returned address is checked (IPv4, IPv6, IPv4-mapped IPv6).
- Loopback, private (10/8, 172.16/12, 192.168/16), link-local (169.254/16), CGNAT (100.64/10), IPv6 ULA/link-local and other non-public ranges are blocked unless the environment has **Allow private network** switched on.
- Cloud metadata endpoints are **always** blocked: `169.254.169.254`, `fd00:ec2::254`, `100.100.100.200`, `metadata.google.internal`.
- **Known limitation:** Chromium and Playwright's request client resolve DNS again when connecting. A hostile DNS server could answer differently between our check and the connection (TOCTOU). FlowCheck does not claim full SSRF protection; only point it at systems you are allowed to test.

## Evidence and sensitive data

- Stored request/response headers redact `Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie` and known secret values (plain, URL-encoded, base64).
- Bodies are stored as text up to 256 KB (truncation is shown); binary bodies are not stored.
- **Screenshots are not redacted.** They can contain personal data and are marked `sensitive`.
- Redaction is best effort, not a guarantee (transformed or split secrets are not detected).

## Secrets

Stored with AES-256-GCM (random IV per value, the project and secret name as authenticated data, so a ciphertext cannot be moved to another secret). Master key: `FLOWCHECK_MASTER_KEY=base64:<32 bytes>`, or a passphrase of at least 16 characters (scrypt, salt in `data/kdf.json`), or the generated `data/master.key`. The API never returns a value; values shorter than 8 characters are rejected (`SECRET_TOO_SHORT`). `{{secrets.name}}` works only in "Type text" values and request headers, never in URLs, paths, query parameters or assertions. A run that needs a missing secret does not start (`SECRET_NOT_FOUND`); the runner decrypts only the secrets the test uses. All step evidence and error messages are scrubbed of known secret values before they are stored — screenshots are not. If the key is lost, secrets and auth profiles cannot be recovered. No key rotation in v1. On Windows the key file's POSIX `0600` mode does not apply; protect `data/` with NTFS permissions of your user profile.

## Login sessions (auth profiles)

The capture browser runs in the runner with the same target guard as runs (allowlist, SSRF checks, service workers blocked). The saved Playwright storage state (cookies, localStorage, IndexedDB) is encrypted with the same master key, bound to its website and session name as authenticated data, and never returned by the API or written to reports. A profile is bound to one website; runs on another one are refused. Each run loads it into a fresh context and never writes it back. A saved session is as powerful as the logged-in user: use dedicated test accounts and delete sessions you no longer need.
